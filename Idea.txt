For PS 26147, I would not build the application as one large Python program where the GUI directly calls GNU Radio/scikit-learn functions. The clean construction is to separate the system into four layers:

```text
┌──────────────────────────────────────────────────────────────┐
│                         FRONTEND                             │
│              React + TypeScript + Visualization              │
│                                                              │
│ Upload │ Configuration │ Signal View │ Analysis │ Results   │
└───────────────────────────┬──────────────────────────────────┘
                            │ REST / WebSocket
                            ▼
┌──────────────────────────────────────────────────────────────┐
│                         BACKEND                              │
│                    FastAPI / Python                          │
│                                                              │
│ API │ Job Manager │ Validation │ Result Manager │ WebSocket │
└───────────────────────────┬──────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────┐
│                    SIGNAL PROCESSING CORE                     │
│                                                              │
│ Preprocess → Isolation → Evidence → Hypotheses → Scoring    │
│                 ↓                                            │
│ Demodulation → Deinterleaving → FEC → Correlation            │
└───────────────────────────┬──────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────┐
│                    DATA / ARTIFACTS                          │
│                                                              │
│ Raw Files │ Intermediate Signals │ Analysis Results │ Logs   │
└──────────────────────────────────────────────────────────────┘
```

The important architectural principle is:

**Frontend should never contain signal-processing logic. Backend should orchestrate the processing core, while the processing core itself should be independently executable and testable.**

The PS specifically requires processing `.IQ`/`.wav`, parameter extraction, modulation identification, demodulation, de-interleaving, FEC, and bit-stream correlation, so those belong in the processing core rather than the UI.

The frontend should be responsible for **interaction, visualization and configuration**, not computation.

I would structure the UI around the actual analysis workflow.

```text

│      ├── Waveform

│      └── Spectrogram
│
├── 04 Automated Analysis
│      ├── Sampling rate estimation
│      ├── Modulation candidates
```

# 3. BACKEND

The backend is the coordinator.

I would use something like:

```text
FastAPI
   │
   ├── File API
   ├── Analysis API
   ├── Configuration API
   ├── Result API
   └── WebSocket API
```

The backend receives something like:

```json
{
  "file_id": "signal_001",
  "format": "iq",
  "sample_rate": 2000000,
  "center_frequency": 145000000,
  "analysis_mode": "automatic"

```

It does not itself perform all the DSP.

Instead:

```text
API
 ↓
Analysis Service
 ↓
Pipeline Manager
 ↓
Core Processing Engine

Results
```

### `upload.py`

Handles:

```text
POST /upload
```

Responsibilities:

* validate `.iq`
* validate `.wav`
* create file ID
* store file
* extract basic metadata

It should not perform demodulation.

---

### `analysis.py`

Handles:

```text
POST /analysis/start
GET  /analysis/{id}
POST /analysis/{id}/cancel
```

It creates an analysis job.

For example:

```text
User clicks "Analyze"
        ↓
POST /analysis/start
        ↓
Create Job ID
        ↓
Start Pipeline
        ↓
Return Job ID
```

---

### `websocket.py`

This becomes important because signal analysis can take time.

Instead of the frontend repeatedly asking:

```text
"Is it finished?"
"Is it finished?"
"Is it finished?"
```

you can stream:

```text
PREPROCESSING       10%
SIGNAL ISOLATION    25%
FEATURE EXTRACTION  40%
CANDIDATE GENERATION 50%
BPSK ANALYSIS       62%
QPSK ANALYSIS       71%
2-FSK ANALYSIS      79%
SCORING             86%
RECOVERY            94%
COMPLETE            100%
```

The frontend can then display the actual processing state.

# 7. Don't hardcode the analysis

This is particularly important for your project.

For example, do NOT write:

```python
if signal_type == "QPSK":
    score = 0.92
```

or:

```python
result = {
    "modulation": "QPSK",
    "confidence": 94
}
```

Those are fake results.

Instead:

```text
raw signal
     ↓
actual DSP
     ↓
features
     ↓
candidate processing
     ↓
measured evidence
     ↓
calculated score
     ↓
result
```

For example:

```text
Candidate: QPSK

Features:
    constellation_error = calculated
    symbol_timing_error = calculated
    spectral_match = calculated
    synchronization_quality = calculated

        ↓

QPSK score = calculated from evidence
```

The same pipeline should run for BPSK, QAM, FSK, etc.

# 8. Candidate architecture

I would make candidates objects rather than hardcoded branches.

Conceptually:

```python
class ModulationCandidate:

    name

    def preprocess(self, signal):
        ...

    def synchronize(self, signal):
        ...

    def demodulate(self, signal):
        ...

    def extract_evidence(self, signal):
        ...

    def calculate_score(self, evidence):
        ...
```

Then:

```text
Candidate Registry

├── BPSK
├── QPSK
├── QAM
├── 2-FSK
└── other supported candidates
```

The pipeline can dynamically select candidates based on configuration.

That gives you a much cleaner architecture.

# 9. Configuration should drive the pipeline

You should have one central configuration object.

For example:

```json
{
  "input": {
    "format": "iq",
    "sample_rate": 2000000
  },

  "analysis": {
    "mode": "automatic",
    "estimate_sample_rate": true,
    "detect_modulation": true,
    "detect_fec": true,
    "detect_interleaving": true
  },

  "modulations": [
    "BPSK",
    "QPSK",
    "QAM",
    "FSK"
  ],

  "deinterleaving": {
    "enabled": true,
    "types": [
      "block",
      "convolutional",
      "diagonal",
      "pseudo_random"
    ]
  },

  "fec": {
    "enabled": true,
    "types": [
      "convolutional",
      "reed_solomon",
      "concatenated",
      "ldpc"
    ]
  }
}
```

Then the backend passes that configuration into the core.

This is much better than scattering configuration throughout the code.

# 12. Where GNU Radio / Python / ML belong

Based on the PS, the processing stack can logically be:

```text
Python
 │
 ├── NumPy
 ├── SciPy
 ├── GNU Radio
 ├── scikit-learn / PyTorch
 └── custom DSP algorithms
```

But don't make ML the entire system.

The architecture should be:

```text
                    SIGNAL
                      │
             Classical DSP
                      │
              Feature Extraction
                      │
             ┌────────┴────────┐
             │                 │
        Rule/DSP evidence      ML evidence
             │                 │
             └────────┬────────┘
                      ▼
                Evidence Engine
                      ▼
             Hypothesis Scoring
```

That fits the problem better than:

```text
IQ → neural network → modulation
```

because the PS involves not just modulation classification but also parameter extraction, demodulation, de-interleaving, FEC and bit-stream correlation.

# 13. Visualization architecture

The frontend shouldn't receive the entire raw IQ file just to draw a graph.

The backend/core should generate appropriate visualization data.

For example:

```text
Raw IQ
  ↓
Core
  ├── waveform data
  ├── FFT data
  ├── waterfall tiles/data
  └── constellation points
          ↓
      API/WebSocket
          ↓
       Frontend
```

Frontend components:

```text
SignalViewer
├── WaveformChart
├── SpectrumChart
├── WaterfallView
└── ConstellationPlot
```

For very large IQ files, you should generate downsampled visualization data rather than sending millions of raw points to the browser.
